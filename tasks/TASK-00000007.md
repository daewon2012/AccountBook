## UI/UX 설계 원칙

- 웹과 모바일은 같은 정보 구조와 업무 용어를 사용한다.
- 거래 등록은 모든 핵심 화면에서 짧은 동선으로 접근할 수 있어야 한다.
- 금액과 상태는 색상뿐 아니라 부호, 레이블과 아이콘으로 구분한다.
- 로딩, 빈 상태, 오류, 권한 없음과 재시도 상태를 화면별로 정의한다.
- 삭제, 복원과 계정 연결 해제 같은 위험 작업은 확인 단계를 제공한다.
- 모바일은 한 손 조작, 안전 영역, 키보드, 오프라인과 재연결 상황을 고려한다.
- 웹은 키보드 탐색, 반응형 레이아웃과 접근 가능한 포커스 이동을 고려한다.

## 작업 지시

1. TASKS.md의 ## 인터페이스 전체를 읽고 TASK-02 웹 작업과 TASK-03 모바일 작업을 빠짐없이 수집한다.
2. 디자인 완료 작업(TASK-..000)은 기준 산출물로 사용하고, 구현 작업(TASK-..001)마다 같은 ID의 tasks/TASK-xxxxxxxx.md 계획 문서를 작성한다.
3. 각 계획 문서는 상태를 PLAN으로 기록하고 다음 내용을 포함한다.
   - 목적과 사용자 시나리오
   - 참조할 화면 정의, 시나리오와 PNG 경로
   - 구현할 화면, 컴포넌트, 상태, 폼과 내비게이션
   - API 계약과 선행 TASK-01 핵심 기능 의존 관계
   - 로딩, 빈 상태, 오류, 권한과 재시도 처리
   - 접근성, 반응형 또는 모바일 기기 제약
   - 완료 조건과 TESTS.md 기준 테스트 계획
4. Web 계획은 Next.js App Router, React, Tailwind CSS, shadcn/ui, React Hook Form, Zod, TanStack Query와 Zustand의 책임을 구분한다.
5. Mobile 계획은 Expo Router, React Native, TanStack Query, Zustand, SecureStore와 기기 Adapter의 책임을 구분한다.
6. Web과 Mobile에 동일한 업무 규칙을 중복 작성하지 않고, OpenAPI 기반 API client와 공통 표시 모델만 공유한다.
7. 핵심 기능, 데이터베이스, HTTP, 파일 저장소와 플랫폼 API에 직접 접근하지 않고 각 계층의 Port/Adapter 경계를 명시한다.
8. 예상 영향 파일은 실제 src/ 또는 scaffold 구조를 먼저 확인한 뒤 기록한다. 구조가 없거나 Architecture 문서와 다르면 Architecture 결정 필요 사항으로 남긴다.
9. 구현 작업별 문서가 완성되면 해당 TASK의 상태를 TODO에서 PLAN으로 변경한다.
10. 웹 공통 셸부터 화면별 작업 순서, 모바일 공통 셸부터 화면별 작업 순서를 정하고 병렬 가능한 작업을 표시한다.

## 기능 목록 자동 등록 지시

1. 작업을 시작할 때 tasks/TASK-00000007/features.md를 읽고 웹·모바일 및 하위 카테고리별 기능을 수집한다.
2. features.md에 기능이 추가되거나 변경되면 같은 작업 안에서 TASKS.md의 ## 인터페이스 마지막에 대응하는 TASK를 자동으로 추가하거나 갱신한다.
3. 웹 기능은 TASK-02, 모바일 기능은 TASK-03으로 시작하는 8자리 ID를 사용하고 기존 2자리 계층 규칙과 충돌하지 않는 다음 번호를 배정한다.
4. TASKS.md에는 하위 카테고리를 유지하고 각 기능의 이름, TODO 상태, 간략한 목표, 완료 조건과 의존 관계를 기록한다.
5. 새 TASK마다 같은 이름의 tasks/TASK-xxxxxxxx.md 계획 문서를 생성하고 상태를 PLAN으로 변경한다.
6. features.md에서 삭제된 기능은 자동 삭제하지 않는다. 기존 TASK의 구현·의존 여부를 확인하고 제거가 필요하면 별도 변경 사항으로 보고한다.
7. 동기화 후 features.md 기능과 TASKS.md 인터페이스 TASK의 누락, 중복, ID 충돌과 잘못된 디자인 경로를 검증한다.
